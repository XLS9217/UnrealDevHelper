# Development philosophy

## Goal

Unreal Dev Helper lets a code agent inspect the same asset structure a developer sees in the Unreal Editor. Inspection must remain accurate, read-only, progressively discoverable, and small enough for an agent to reason about.

Build for correctness and shared understanding first. Optimize only after comparing the returned data with the corresponding Unreal Editor view.

## One uasset is one virtual tree

Every request selects exactly one asset with `asset_path`. The inspector presents that asset as a type-specific virtual tree.

```text
asset_path
└── /
    ├── identity
    ├── type-specific sections
    └── terminal values or structures
```

Each inspector defines the tree that naturally represents its asset type. Do not force unrelated Unreal asset classes into one artificial schema.

Examples:

```text
Blueprint
/
├── identity
├── class_defaults
├── components
├── variables
├── interfaces
└── graphs

Blackboard
/
├── identity
├── parent
└── keys

Behavior Tree
/
├── identity
├── blackboard
└── graph

Environment Query
/
├── identity
└── graph
```

## Outline and detail are separate operations

Expose two operations:

```text
inspect_uasset_outline(asset_path, node)
inspect_uasset_detail(asset_path, node, full)
```

`outline` is navigation. It returns only the selected node's immediate children, their paths, their kinds, and whether they can be expanded.

`detail` is data. It returns the actual value or complete subtree represented by the selected node.

The normal agent workflow is:

```text
root outline
→ section outline
→ selected detail
→ deeper traversal only when useful
```

Do not require an agent to request root detail merely to discover what an asset contains.

## Terminal visual graphs

A graph that is primarily understood as one visual structure should be terminal in the outline. The agent selects the graph and receives the complete graph detail in one request.

This currently applies to:

- Individual Blueprint graphs such as `/graphs/EventGraph`
- Behavior Tree `/graph`
- Environment Query `/graph`

Do not expose every graph node and pin as further outline levels by default. The first objective is for the agent and developer to look at the same complete logical structure.

> The agent sees what I see, so we are on the same page.

This is a required extension rule, not a temporary implementation detail. When adding any new graph-like uasset or graph section:

1. Stop outline traversal at a terminal graph node.
2. Return the entire selected graph as one detail payload.
3. Dump that payload and compare it with the Unreal Editor graph.
4. Do not implement graph-node, pin, transition, test, or branch outline traversal unless the user explicitly asks to change this philosophy.
5. Do not add semantic parsing until the complete agent-visible graph has been reviewed with the user.

A new inspector is incomplete if a fresh agent must recursively traverse internal graph nodes merely to see the logical structure visible on one Editor canvas.

## Native C++ reader, optional Python interpretation

Keep the boundary clear:

```text
C++ plugin
├── load the asset in its real project context
├── access native/editor-only Unreal APIs
├── resolve virtual-tree nodes
├── return the selected native structure
└── report factual metadata

Python application
├── transport requests
├── optionally perform secondary semantic parsing
├── adapt results for an agent
└── serve CLI and future MCP interfaces
```

C++ should be an authoritative native reader, not a growing collection of presentation heuristics. Python is the preferred location for secondary transformations that can be derived from native data, such as:

- Removing disconnected Blueprint graph nodes
- Removing unused pins
- Deduplicating reciprocal links
- Replacing GUIDs with short local IDs
- Converting native graph storage into semantic nodes and connections

Keep Unreal-only decisions in C++. Examples include loading assets, comparing CDO properties with a parent CDO, checking whether a pin matches its autogenerated default, and accessing Behavior Tree or EQS structures unavailable to Unreal Python.

## Full and agent-facing detail

`full` changes detail representation, not traversal scope.

- `full=false` returns the agent-facing filtered or parsed representation.
- `full=true` returns the complete human/debug representation for the same selected node.

The CLI intentionally exposes only agent-facing detail. Human comparison scripts may call `UnrealApplication` with `full=True`.

Never use `full` to mean "inspect the entire asset." The selected virtual node still controls scope.

## Optimize type by type

Do not create a generic optimization framework before understanding an asset type's real Editor representation.

Use this process:

1. Define the asset's natural virtual tree.
2. Return the complete native detail for a selected node.
3. Dump the exact agent-facing and full responses.
4. Compare both responses with what the developer sees in Unreal Editor.
5. Identify redundant storage details versus meaningful authored information.
6. Add a type-specific Python parser only when the desired semantic representation is clear.
7. Preserve the native full response for debugging and future parsers.

Blueprint graph parsing follows this process. Behavior Tree and EQS graphs currently remain unparsed so their native output can be evaluated first.

## Prefer authored information

Agent-facing output should emphasize what the developer authored or connected.

Examples:

- Blueprint class defaults: properties different from the parent CDO
- Blueprint graphs: connected logic and explicitly authored input values
- Blackboard: declared keys and their configured types
- Behavior Tree: complete tree, decorators, services, and task structure
- EQS: options, generators, tests, and configured descriptions

Do not discard information merely because it is false, empty, inherited, or disconnected until its meaning is understood for that asset type. Filtering rules must follow semantics, not only JSON shape.

## KISS constraints

- Keep one asset path per request.
- Keep outline and detail APIs primitive and explicit.
- Keep routing in the native library.
- Keep one inspector class per supported asset type.
- Avoid caches until measured request cost justifies them.
- Avoid Python fallbacks that pretend native plugin support exists.
- Avoid speculative schemas for asset types not yet inspected against real project examples.
- Prefer a small working type-specific implementation over a broad abstraction.

## Read-only boundary

All current inspection operations are read-only. They must not modify properties, compile assets, save packages, or mutate the Editor world.

Arbitrary `execute-python` is also restricted to read-only investigation. Future write support must use explicit reviewed application operations and fixed scripts rather than free-form remote Python.

## Validation workflow

Native source changes require rebuilding the game's Editor target and restarting Unreal before Python can call the new DLL API.

For each inspector change:

1. Compile-check the modified C++.
2. Close Unreal if it holds the plugin DLL during linking.
3. Rebuild and reopen the project.
4. Run the relevant dump script.
5. Confirm `inspection.ok` for every response.
6. Compare outline, agent-facing detail, full detail, and the Unreal Editor view.

Treat missing Python-exposed methods after a source change as an old DLL problem first, not as evidence that the Python transport is broken.
